# 夜间纪事必须从“概括报告”改为“故事时间轴”

## 一、为什么改（用户明确确认）
当前呈现类似：
> 昨夜至今晨，我陆续做了些事：调息温养、研读……。眼下仍是寻常日子……

用户明确不喜欢这种笼统、同质化的报告，更喜欢此前提议的：
> **00:00 温知遥因旧伤……**  
> **00:15 温知遥……**  
> **06:40 温家……**

目标是让玩家感觉自己睡着时，姐姐仍有**具备时间连续性、因果、生活细节**的行动；不是 AI 替她临时编人生，不是空洞日报，亦不能变成冷冰冰日志管理页。

## 二、期望 UI（示意内容，不是真实已发生事件）
**昨夜纪事｜10月17日夜—10月18日晨（北京时间）**

**00:00**　温知遥因旧伤隐痛，睡得并不安稳。她在榻上醒了片刻，慢慢调匀气息。  
**00:15**　她将凌乱的药方挪到枕边理好，终究没有勉强起身。  
**02:30**　檐下风声渐轻，她合眼歇下，呼吸也渐渐平稳。  
**06:40**　温家传来一纸问询。她没有硬撑着外出，只把来信收好，打算身体稍稳再与你商量。  
**07:20**　她稍醒，察看身边的药盏，继续在床上静养。  

**小字提示（可折叠）**：“以上时刻为游戏世界内已记录事件；本次暂无新的主线分支。”

**最重要的约束**：这些是期望视觉文风的**假设演示**。正式游戏仅当规则引擎**真的生成并保存**相应事件后，才显示那条时刻与内容。不能为了让列表好看，就造每天 00:15 整理药方、06:40 温家传令；如夜里只有两件真事，则只显示两条。若没有可靠事件，显示“昨夜平静，无额外事件记录”，不可虚构。

## 三、现有可复用代码与差距（截至 main `554afdf...`）
- `engine.js::advanceAutonomy` 已产生 `s.life.ledger`（事件 `id`、`at`、`kind`、`activity`、`text`、`bodyState`、`delta`）；小时槽目前大致 `[0,6,9,12,16,20,23]`，且离线只回补有限天数/有限事件，不保证 00:15 或 06:40 的任意分钟存在。
- `engine.js::nightRecap` 已有 `rhythmState.recaps`，记录 `id,date,at,text,eventIds`，但只去重 activity 生成总述；是“已有事件、丢失展示时间”的可改造基础。
- `app.js::presentRecap` 和 `renderStage` 会把 recaps 转成一个 `<p>` 文字，**没有逐时点 DOM 结构**；应改成“时间轴列表/事件卡”，保留旧摘要记录的兼容展示。
- `world.js` 已有权威场景日程和受伤限制，`companion.js` 有寝居只读场景快照；来信/寝居/纪事应一致。
- `life.ledger` 内已有的事件是**模拟世界状态机产生的游戏事实**，不是现实真实活动。纪事应明确“故事世界内时间”，不能把生成时间混成真实世界观测。

## 四、建议的数据契约（仅是设计提案，不能当作当前代码事实）
每个夜间事件：
```json
{
  "eventId": "life:v5:2026-10-18:0000:injury-rest:01",
  "occurredAt": "2026-10-18T00:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "kind": "rest",
  "importance": "ordinary",
  "location": "bedroom",
  "bodyState": "ill",
  "actionId": "bed_light_nap",
  "factText": "旧伤不适，卧榻调息",
  "narration": "温知遥因旧伤隐痛……",
  "sourceEventId": "life:v4:2026-10-18:0",
  "sourceType": "engine-ledger",
  "delta": {},
  "plotGate": "chapter-9-preparation",
  "visualClip": "rest_pillow"
}
```
**说明**：上述 ID / `occurredAt` 是示意。`narration` 只能根据 `factText` 润色，不能新增世界事实；`actionId/visualClip` 只用于**已有可播放资格**的演出。如果真实事件是“凌晨在榻上调息”，绝不擅自写“她半坐翻书喝药”。

## 五、事件生成与回放：实现顺序
1. **先查权威事件源**：保留 `life.ledger`, `chronicle`, `supervision.deadlines`, `rhythmState.recaps` 原数据。按当前代码的北京时间日界线构建 18:00 昨天→今日早晨的窗口，收集**确已发生、未处于时钟争议**的事件。
2. **先能展示精确时间再考虑新增分钟级细节**：第一阶段直接渲染 ledger `at` 并配 `title/text`；不得把固定 `[00:00,06:00]` 凭展示需求假称为 `00:15,06:40`。
3. **第二阶段增加生活子事件**：若想有 00:15 的整理药方、06:40 的来信，必须由事件状态机在该时刻**真正写入** stable ID、来源、前置条件和叙事后置条件。时间可在允许窗口通过“用户时区北京 + 稳定种子 + 状态条件”确定，不依赖每次新 `Math.random()`；两设备、离线重播得到同一 ID/时刻。
4. **人物伤病门控**：旧伤夜醒是*可能事件*而非天天必发；重伤/病中只可卧榻/调息/床边应对，不准凌晨离床查药、去药庐、强行读书；健康时可正常夜间活动。温家压力/净化必须满足剧情引擎约束，绝不能凭描写新增 DDL 惩罚。
5. **同步/去重**：`eventId` / `sourceEventId` 幂等、按 `occurredAt` 稳定排序，同时间事件按重要性及稳定 ID 排序；补算时仅补缺，不能双重结算健康/压力/修为。跨设备同步以现有合并规则为权威，冲突时保守展示并提示核对。
6. **快照一致性**：纪事每条可带 `location`、`bodyState`、`actionId`、`sourceType`；前端展开重要事件可演出已批准的 clip，**缺 clip 则只保留文本**，不可报“已动画演出”。若事件尚未写入，在线 AI 也不能先把它当已发生事实。
7. **旧记录兼容**：旧 recap 文本/ID 不删、不覆盖。已记录 `eventIds` 若能在 ledger 找到真实 `at`，按真实时刻衍生新的只读时间轴；若找不齐，则保留“旧版概述（具体时刻未保存）”，不反向编造时间。给老记录加 `formatVersion` 渲染兼容即可，**不因新格式重复奖励/重罚**。
8. **UI 改造**：来信阅读器里“夜间纪事”从一个长 `<p>` 改成 `<ol class="wd-night-timeline">`，每项显示北京时间 `HH:mm`、一句有画面感的叙述和（可折叠）可信来源/重要事件按钮。普通日常一行；重要/重大事件有“查看详情/进入剧情”，但必须符合解锁与 AU 授权。
9. **通知/阅读体验**：起床后可自愿打开，不要求每次清醒确认、不在专注中弹窗；无真实推送能力不能伪称离线实时通知。长纪事保留滚动位置、日期选择、合理折叠；重大事件优先置顶提示，但时间轴仍按时间顺序。

## 六、文案设计标准
- 时间写在**事件左侧**，正文像小说的第三人称短句。避免“昨夜我陆续……”泛化，以及每项机械地复制 `LIFE_ACTIONS.text`。
- 日常可有动词及轻微感官细节，但不能新增已确认事实：例如规则只有“卧榻休息”可写“她闭目调息”，不能写“咳出血”“收到急信”“被责罚”。
- 含已发生的温家来函要写“何时到、姐姐如何处理、后续打算”，不可从“有压力”推断出具体谁来了。
- 病情、陪伴修炼、主线因果连贯：昨天有严重伤势，夜里表现需有疲乏/温养；今天仍显示同一长期伤病，不会因晨起‘复原’。
- AI如果参与润色，只给**结构化白名单事实**，输出只允许措辞修饰，新增实体/地点/处罚/状态动作一律拒绝；接口故障时可用规则模板生成同样可用的文字时间线。

## 七、建议单独测试的例子
- 10月17日 23:00 → 10月18日 00:00 → 06:00：跨日排序和“昨夜”标题准确；用户时区不是北京也按北京时间。
- 仅记录一条 `00:00` 事件：展示一行，不填充四条假的。
- 旧伤活跃 + 问询到来：只能在床边收信和调息，不能走动或起坐；**旧伤与问询发生要有真实 ledger/剧情触发证据**。
- 录入 DDL 逾期/跨端合并：既有事件只结算一次，不因为纪事可视化重复扣血。
- 旧 `recap:date` 没有 eventIds：保留旧摘要，提示“旧记录无完整分钟事件”。
- 设备时钟逆跳、离线超过可回补范围、后台长停：不生成未经核对的纪事，不补播大量角色演出。
- 打开地图/阅读来信/回到专注：原计时持续正常、夜间纪事不覆盖角色或 HUD。
